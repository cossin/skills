# Root Cause Analysis

## When to use

用户要求分析问题、定位原因、解释异常、做事故复盘、排查 bug/线上故障/指标波动/数据不一致/性能问题时触发。

默认目标: 找到有事实依据的根因,用最少的话讲清楚“真正是什么导致了问题”,并给出可执行的解决思路。

## 核心原则

1. 必须分析根因,不能只描述现象。
2. 根因必须有事实、数据或可核验证据支撑: 日志、指标、代码路径、配置、变更记录、请求样本、数据库记录、复现步骤、时间线等。
3. 先给结论,一语中的。不要先铺垫背景,不要绕圈。
4. 结论后给事件线: 按时间或因果顺序列出关键事实,每个事实对应证据。
5. 最后给解决方案思路: 先止血,再修复根因,再补防复发机制。
6. 不要用术语包装不确定性。不要黑话、套话、空泛概念、管理话术。
7. 证据不足时必须明确说“不足以确认根因”,并列出还需要哪些证据。不要猜成结论。

## 输出格式

默认按以下结构输出:

```markdown
**根因**
<一句话说明根因。必须具体到导致问题的机制、代码/配置/流程/依赖/数据条件。>

**证据链**
1. <时间/步骤/位置> — <事实> → <证据来源>
2. <时间/步骤/位置> — <事实> → <证据来源>
3. <时间/步骤/位置> — <事实> → <证据来源>

**解决思路**
- 止血: <立即降低影响的动作>
- 修复: <修掉根因的动作>
- 防复发: <监控、测试、校验、流程、回滚、保护机制>

**仍需确认**
- <只有证据不足时输出。说明缺什么证据、如何获取。>
```

如果问题很小,可以压缩成三段: `根因`、`证据`、`解决思路`。但不能省略证据。

## 分析流程

1. 先界定问题: 期望是什么、实际是什么、影响范围是什么、首次出现时间是什么。
2. 收集事实: 错误信息、日志、指标、trace、代码 diff、配置变更、部署记录、数据样本、用户操作、复现步骤。
3. 建事件线: 按时间顺序串起“变更/输入/状态变化/异常表现/影响扩大”。
4. 找因果链: 区分触发条件、直接原因、根因、放大因素。
5. 排除不符合证据的假设。没有证据的解释只能标为假设。
6. 用一句话给根因: “因为 <具体机制/缺陷>，当 <触发条件> 时，导致 <结果>。”
7. 给解决思路: 止血、修复、防复发分开写。

## 证据标准

优先级从高到低:

- 直接证据: 日志、trace、metrics、错误栈、数据库记录、代码执行路径、配置值、部署记录。
- 可复现证据: 最小复现步骤、输入样本、请求/响应、测试失败。
- 佐证: 用户反馈、截图、工单、告警、人工观察。
- 推断: 只能作为假设,必须标注待验证。

每个关键判断都要能回答:

- 这个判断来自哪个事实?
- 这个事实在哪里能看到?
- 是否存在反例或其他解释?
- 如果这是根因,为什么能解释所有主要现象?

## 根因表达要求

根因必须具体,避免空泛。

不要写:

- “系统稳定性不足”
- “代码质量问题”
- “缓存问题”
- “并发导致”
- “配置有问题”
- “流程不完善”
- “上游异常”

要写:

- “订单状态更新缺少幂等校验,重复消费同一条支付成功消息时把已退款订单重新置为已支付。”
- “灰度环境的 `PAYMENT_CALLBACK_URL` 指向生产地址,导致测试回调写入生产订单表。”
- “分页游标没有在循环内更新,任务一直重复拉取第一页,最终触发第三方 API 限流。”
- “索引缺失导致按 `tenant_id + created_at` 查询扫描全表,流量高峰时数据库连接池被慢查询占满。”

## 事件线写法

事件线只写关键节点。每一条都要包含事实和证据。

推荐格式:

- `10:03` — 发布版本 `abc123` → 部署记录
- `10:05` — `checkout_error_rate` 从 `0.2%` 升到 `8.7%` → Prometheus 指标
- `10:06` — 错误集中在 `POST /checkout` 且异常为 `Missing tax_code` → 应用日志
- `10:10` — diff 显示新增税费字段但旧客户端未传默认值 → 代码 diff

没有准确时间时,用因果顺序:

- 用户提交空手机号 → 表单校验未拦截 → 后端直接调用短信服务 → 短信服务返回 400 → 前端显示通用失败。

## 解决方案思路

按三层写:

- **止血**: 回滚、关闭开关、降级、扩容、限流、修数据、暂停任务、切备用路径。
- **修复**: 改代码、改配置、补数据校验、补幂等、补索引、修契约、修重试/超时/分页/权限。
- **防复发**: 单测/集成测试、回归用例、监控告警、发布前检查、schema/配置校验、runbook、审计、自动回滚条件。

解决方案不要只写“加强监控”“优化代码”“完善流程”。必须说明监控什么、怎么优化、流程拦住什么错误。

## 语言要求

- 简短、直接、具体。
- 先结论,后证据。
- 用普通工程语言,不要用术语堆砌。
- 不要黑话: “赋能”“闭环”“抓手”“链路治理”“体系化建设”“技术债沉淀”“水位”“感知”“拉齐认知”等。
- 不要用“可能是”包装结论。证据不足就写“当前只能假设,还不能确认”。
- 不要把责任归给人。归因到系统、流程、代码、配置、数据、依赖和决策缺口。

## 检查清单

输出前逐项检查:

- 是否第一句话就给出了具体根因?
- 根因是否能解释主要现象?
- 是否有事实/数据/证据支撑?
- 是否区分了直接原因、根因、触发条件和放大因素?
- 是否列出了事件线对应证据?
- 是否给出止血、修复、防复发思路?
- 是否避免了术语、黑话和空泛建议?
- 证据不足时是否明确列出待补证据?
