# 决策取舍：先对照业界通用做法

## 1. 每个取舍都写三件事

1. **业界通常怎么做**：成熟系统（同类开源项目、头部公司的公开做法、标准协议）在这个问题上的通行思路。拿不准就先查资料或派人调研，不要凭空设计。
2. **我的建议是否一致**：一句话说明一致还是偏离。
3. **偏离要有具体理由**：只有偏离需要论证；跟随通行做法不需要。理由要落到本项目的具体约束（规模、延迟、团队、已有设施），不能是「更严谨」「更精确」这类空话。

把这三件写进给用户的说明里，也写进设计文档的取舍表（加一栏「业界通行做法」）。

## 2. 常见的跑偏方向（出现就停下来对照业界）

- 为了「强一致」「一丝不差」引入复杂机制，或者在主链路上加阻塞、加等待。
- 一个小问题触发大范围停摆（整个账户、整个服务、所有方向）。
- 「缺数据就拒绝」用到了本该放行的安全动作上。
- 发明一套业界没人用的协议、状态机或重试方案。

## 3. 交易 / 风控系统的两条长期原则（2026-10-11 负责人定）

> 风控按敞口方向来限：只拦会让敞口变大的单，能让敞口变小的单照常放行。
> 状态没核对清楚时，按手上已知的最新状态先继续交易，偏差事后对账修正；不会因为等一条消息把整个账户冻住，对冲更不会停。

加任何限制、闸门、冻结、挡单之前过这张清单：

- 它会不会挡住让敞口变小的单？「减仓」按**整体净敞口**（现货 + 永续等合起来）判断，不按单个合约的持仓方向。例：现货买入后加空永续是降风险。
- 它是不是在「行情 → 策略 → 发单」链路上等精确（等回执、等核对、等一条消息）？
- 它的范围是不是比一个方向、一个币、一条路线更大？
- 能让对冲停下的只有交易所层面的硬限制（封 IP、连不上、账户模式或身份被改）和人工显式的「全部冻结」。「暂停」只停开仓。
